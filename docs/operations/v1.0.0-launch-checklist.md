# Athlya v1.0.0 — Phase A : Stabilisation prod (Jour 0 → Jour 7)

Runbook consolidé pour la sortie v1.0.0. Il agrège les 9 runbooks ops du dossier `docs/operations/` en une checklist linéaire actionnable, avec ordre d'exécution, critères de validation et points de bascule.

**Périmètre** : tagger v1.0.0, provisionner les services externes (ZAP / Checkly / Sentry / Axiom), valider 7 jours de production silencieuse, et acter le go-live d'un premier studio pilote en mode lecture seule.

**Pas inclus** : démarrage v1.1 (mobile), promotion d'items post-1.0, modifications de scope. Ces décisions arrivent en Phase B (semaines 2-3).

---

## 🎯 Critères de succès Phase A

À la fin du Jour 7, **toutes ces conditions doivent être vraies** pour valider la Phase A :

- ✅ Tag `v1.0.0` taggé sur `main` et poussé sur l'origin avec une release GitHub publiée.
- ✅ ZAP scan vert (zero high-severity finding) sur l'environnement staging, déclenché automatiquement sur PR.
- ✅ Les 4 checks Checkly (CK1 liveness, CK2 readiness, CK3 list-classes, CK4 web login) sont verts pendant 7 jours consécutifs.
- ✅ Sentry projet créé, DSN configuré sur le Worker, au moins 1 event de test capté avec `traceId` correct.
- ✅ Les 13 alertes Axiom + Slack/PagerDuty sont armées et silencieuses (aucune alerte non-test n'a tiré).
- ✅ Aucun breach de SLO sur 7 jours (availability ≥ 99.9 %, p99 < 500 ms, error rate < 0.1 %, booking success > 99 %).
- ✅ Aucune entrée dans la DLQ Cloudflare Queues, ou ≤ 1 entrée explicable.
- ✅ Premier studio pilote provisionné en mode lecture seule, ses utilisateurs peuvent browse les classes.

Si **un seul** critère est rouge, ne pas passer en Phase B — corriger ou documenter le rollback dans cette même checklist.

## Day 1 — Provisioning ZAP + Sentry (~2h)

### 1. ZAP baseline scan

Suivre [`zap-activation.md`](./zap-activation.md) — runbook 5 étapes.

- [ ] **Étape 1** : confirmer staging URL stable (ex : `https://api-staging.athlya.app`).
- [ ] **Étape 2** : provisioning `ZAP_TARGET_URL` comme **repository variable** (PAS secret) :
  - GitHub repo → Settings → Variables → Actions → New repository variable
  - Name : `ZAP_TARGET_URL`
  - Value : URL staging avec `https://`, sans trailing slash.
- [ ] **Étape 3** : test via `workflow_dispatch` :
  ```bash
  gh workflow run zap-baseline.yml
  gh run watch
  ```
- [ ] **Étape 4** : valider les findings initiaux (HSTS, CSP, X-Content-Type-Options). Tous les findings actuels doivent être **acceptés ou ignorés** dans `.zap/rules.tsv`.
- [ ] **Étape 5** : confirmer activation automatique sur PRs (workflow trigger `pull_request`).

**🚦 Validation ZAP** : un PR factice (ex : modification du README) déclenche ZAP automatiquement, le scan termine sans high-severity finding non-listé dans `.zap/rules.tsv`.

### 2. Sentry projet + DSN

- [ ] Créer un projet Sentry **JavaScript / Cloudflare Workers**.
- [ ] Récupérer le DSN.
- [ ] Provisionner sur les 3 environnements via `wrangler` :
  ```bash
  echo "<DSN>" | wrangler secret put SENTRY_DSN --env production
  echo "<DSN>" | wrangler secret put SENTRY_DSN --env staging
  ```
  (En dev, le client doit fail-OPEN si `SENTRY_DSN` absent — c'est la sémantique implémentée Sprint 12.)
- [ ] **Test event captured** : invoquer une route qui throw (ex : `/v1/__test_500` si flag dev) en staging, vérifier dans Sentry que :
  - L'event apparaît avec son `traceId`.
  - Le tag `traceId` permet le pivot vers Axiom.
  - Le breadcrumb du middleware OTel est présent.
- [ ] **Performance** : activer Sentry Performance avec sample rate 0.05 (5 %) en prod, 1.0 en staging.

**🚦 Validation Sentry** : 1 event de test visible avec breadcrumbs cohérents et `traceId` exploitable.

## Day 2 — Provisioning Axiom + Checkly (~3h)

### 1. Axiom alertes

Suivre [`axiom-alerts.md`](./axiom-alerts.md) pour les définitions exactes.

- [ ] Confirmer le dataset `athlya-api` reçoit bien les spans OTel + logs JSON depuis les 3 envs.
- [ ] **Provisionner les 13 alertes** :
  - 4 SLO burn rates (availability, latency p99, error rate, booking success)
  - 9 incident alerts (DLQ non-vide, JWKS rotation expirée, Stripe webhook signature fail, RLS violation tentative, audit log immutability breach, circuit breaker open, login anomaly spike, HIBP service down > 5min, cron RGPD échec)
- [ ] Pour chacune : configurer destination **Slack** (incident-low) ou **PagerDuty** (incident-high) selon `axiom-alerts.md`.
- [ ] Test : déclencher manuellement chaque alerte via une query factice (ex : `count() > 0` sur `error.severity = "test"`) puis désarmer.

**🚦 Validation Axiom** : les 13 alertes sont armées, état "Healthy", aucune en `Firing`.

### 2. Checkly synthetic monitoring

Suivre [`synthetic-monitoring.md`](./synthetic-monitoring.md).

- [ ] Compte Checkly free tier provisionné.
- [ ] **CK1 — liveness** : `GET /health` toutes les 60 s, depuis 2 régions (eu-west-1 + us-east-1). Threshold p99 < 200 ms.
- [ ] **CK2 — readiness** : `GET /health/ready` toutes les 5 min, valide DB + Redis ping. Alert sur 2 fails consécutifs.
- [ ] **CK3 — list-classes (API)** : `GET /v1/classes` avec studio synthétique seedé en staging, toutes les 5 min. Threshold p99 < 500 ms (SLO Req 23.2).
- [ ] **CK4 — web login (Playwright recorder)** : flux login complet sur `apps/web` staging, toutes les 15 min.
- [ ] Alert routing : Slack pour CK1/CK3, PagerDuty pour CK2/CK4.

**🚦 Validation Checkly** : les 4 checks tournent depuis 1h, tous verts, alertes routées correctement (vérifier en muant volontairement le staging puis en restaurant — bandeau Slack doit apparaître + cleared).

### 3. Cost queries Axiom

Suivre [`synthetic-monitoring.md`](./synthetic-monitoring.md) section "Cost queries".

- [ ] **Per endpoint** : query `summarize sum(http.duration_ms) by http.route`.
- [ ] **Per studio** : query `summarize count() by studio.id` sur les 7 derniers jours.
- [ ] Sauvegarder en favorites Axiom — pas d'alerte armée encore (baseline à établir Phase B).

## Rollback procedure (urgence)

Si un incident critique est détecté pendant Phase A :

### Niveau 1 — Rollback runtime (5 min)

```bash
# Lister les versions Workers déployées
wrangler versions list --env production

# Rollback à la version pré-v1.0.0
wrangler rollback <previous-version-id> --env production
```

### Niveau 2 — Rollback DB (15 min)

Si une migration v1.0.0 a corrompu un état :

```bash
# Voir packages/db/migrations/README.md pour les .down.sql disponibles
psql $DATABASE_URL -f packages/db/migrations/0XXX_xxx.down.sql
```

⚠️ **Vérifier toujours en staging d'abord**. Les migrations à rollback documentées : `0000_init`, `0001_rls`, `0002_export_jobs` (Sprint 1, H7).

### Niveau 3 — Communication studio pilote

- [ ] Slack channel `#athlya-incidents` : message public format Sprint 12 runbook (`docs/runbooks/incident-template.md`).
- [ ] Email au studio pilote avec ETA fix.
- [ ] Update de status page si provisionnée.
