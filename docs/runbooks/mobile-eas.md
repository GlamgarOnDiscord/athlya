# Runbook: Mobile builds and store release (EAS)

> Operator steps to build and publish `apps/mobile` with Expo Application Services.
> Nothing here is automated in CI yet: CI only lints, typechecks and tests the package.

`apps/mobile/eas.json` declares two build profiles and holds **no secret**:

| Profile      | Distribution            | Use                                   |
| ------------ | ----------------------- | ------------------------------------- |
| `preview`    | internal (ad hoc / APK) | pilot studio testers, QA              |
| `production` | store (AAB / App Store) | Google Play and App Store submissions |

Build numbers are managed remotely by EAS (`appVersionSource: remote`, `autoIncrement` on
`production`). The marketing version lives in `apps/mobile/app.json` (`expo.version`).

## 1. One-time setup

1. Create (or reuse) the Expo organization that owns Athlya and add the operators as members.
   Use an organization account, not a personal one, so ownership survives staff changes.
2. Install the CLI locally: `pnpm dlx eas-cli@latest login` (any release satisfying
   `cli.version` in `eas.json`).
3. From `apps/mobile`, link the project: `pnpm dlx eas-cli@latest init`. This writes
   `expo.extra.eas.projectId` and `expo.owner` into `app.json`. The project id is not a secret:
   commit that change in a PR.
4. Identifiers are already set in `app.json`: iOS `bundleIdentifier` and Android `package` are both
   `app.athlya.mobile`. Changing them after the first store release is not possible.

## 2. Environment variables

The API origin is public and pinned per profile in `apps/mobile/eas.json`:

| Variable              | `preview`                        | `production`             |
| --------------------- | -------------------------------- | ------------------------ |
| `EXPO_PUBLIC_API_URL` | `https://staging.api.athlya.app` | `https://api.athlya.app` |

There is no fallback: `app.config.js` fails any EAS build whose profile does not set
`EXPO_PUBLIC_API_URL`, and the app refuses to boot without it (local runs must export it).
`EXPO_PUBLIC_*` values are inlined into the JavaScript bundle and are public by design: no server
secret may ever use that prefix. Real secrets, if any are ever needed, go to expo.dev (Project →
Environment variables, "secret" visibility), never into the repository.

Sign-in and registration also need the API side of the Turnstile WebView (#649): the API host in
the widget's allowed hostnames and `TURNSTILE_SITE_KEY` on the auth Worker of each environment. Steps
in [`docs/mobile/README.md`](../mobile/README.md#operator-steps). Do it before handing a `preview`
build to testers, or every sign-in fails on the security check.

## 3. Credentials

Let EAS manage signing credentials (stored encrypted on Expo's servers):

- **iOS**: `pnpm dlx eas-cli@latest credentials -p ios`, sign in with the Account Holder, an Admin,
  or an App Manager who was granted "Access to Certificates, Identifiers & Profiles" (the plain
  App Manager role cannot create certificates). EAS creates the distribution certificate and the provisioning
  profiles. Create the App Store Connect app record for `app.athlya.mobile` first.
- **Android**: `pnpm dlx eas-cli@latest credentials -p android` and let EAS generate the upload
  keystore. Download a backup of the keystore to the team password manager immediately: losing it
  blocks every future Play update.
- **Submit keys**: an App Store Connect API key (`.p8`, Admin or App Manager) and a Google Play
  service-account JSON with release permissions. Keep both files **outside the repository** (for
  example in the password manager) and upload them through `eas credentials` / expo.dev. The
  patterns in `apps/mobile/.gitignore` and gitleaks in CI are only a safety net for the usual file
  names, not a reason to keep the files in the working tree.

## 4. Build

From `apps/mobile`:

```bash
pnpm dlx eas-cli@latest build --profile preview --platform all
pnpm dlx eas-cli@latest build --profile production --platform all
```

EAS installs the monorepo with pnpm, then runs the `eas-build-post-install` script, which builds
`@athlya/shared` (Metro resolves it through `dist/`). Native projects are generated by prebuild on
the build server; `ios/` and `android/` are never committed.

## 5. Submit

```bash
pnpm dlx eas-cli@latest submit --profile production --platform ios --latest
pnpm dlx eas-cli@latest submit --profile production --platform android --latest
```

Fill `submit.production` in `eas.json` (App Store Connect app id, Play track) through a PR the first
time; those identifiers are not secrets.

Store listing checklist before the first public release:

- Privacy policy URL (the web app's `/privacy` page) and the data-safety / privacy-nutrition forms,
  consistent with [`docs/compliance/expo-push-transfers.md`](../compliance/expo-push-transfers.md).
- Face ID usage string (set in `app.json` through the `expo-local-authentication` plugin).
- Bluetooth (connected machines and heart-rate straps, `react-native-ble-plx` plugin in
  `app.json`): iOS `NSBluetoothAlwaysUsageDescription`; Android `BLUETOOTH_SCAN`
  (`neverForLocation`) and `BLUETOOTH_CONNECT`, plus location for Android 11 and lower only. No
  background mode. Declare the Bluetooth use in the privacy forms: live machine data and heart
  rate (health data) stay on the device until the member logs the session; RR-intervals are never
  stored, and only the last strap's id and name are remembered on the device. The usage string
  is native configuration: a change to it ships with the next EAS build.
- Export compliance: besides HTTPS, the app encrypts its offline queue on device with AES-256
  (MMKV). `app.json` deliberately does not declare `ITSAppUsesNonExemptEncryption`: answer the
  encryption questions in App Store Connect on the first submission (data-at-rest encryption with
  standard algorithms is usually exempt, but the answer belongs to whoever signs the submission),
  then pin the result in `app.json` through a PR.
- Store artwork: start from `assets/brand/` (A-mi mascot, see `docs/brand/README.md`); the app icon
  and splash already use it.

## 6. Rollback

There is no OTA update channel (`expo-updates` is not installed). To roll back, rebuild and submit
the previous git tag, or halt the staged rollout in Play Console / App Store Connect.
