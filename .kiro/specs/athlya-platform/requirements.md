# Requirements Document

## Introduction

Athlya is an open-source, multi-tenant, event-driven, RGPD-first fitness platform designed as an alternative to proprietary SaaS solutions (bsport, Mywellness, Mindbody). It serves boutique studios (yoga, crossfit, boxing), mid-size chains, independent coaches and sports communities, with strong commitments on data ownership, resilience by design and edge-first performance.

These requirements are derived from the approved design document. They cover the eight business domains (Auth, Members, Reservations, Content, Billing, Notifications, Analytics, AI/Coach), the cross-cutting platform capabilities (API gateway, event bus, multi-tenant isolation, offline sync) and the non-functional constraints (performance, availability, security, privacy, accessibility, internationalization). The target SLO is p99 < 500 ms on the reservation API, 99.9% monthly availability and zero double-booking under contention.

## Glossary

- **Athlya_Platform**: The complete system composed of client applications, the edge API gateway, domain services, the event bus and the persistence layer.
- **API_Gateway**: The edge HTTP entry point implemented in Hono 4 on Cloudflare Workers. Responsible for TLS termination, authentication, rate limiting, Zod validation, routing and tracing.
- **Auth_Service**: The domain service handling identities, sessions, OAuth providers, biometric unlock and RBAC (built on Better Auth).
- **Members_Service**: The domain service handling member profiles, consents, subscription history and RGPD export.
- **Reservations_Service**: The domain service handling class planning, bookings, waitlist, cancellation and check-in.
- **Content_Service**: The domain service handling studio-owned content (classes, media assets stored in Cloudflare R2).
- **Billing_Service**: The domain service integrating Stripe for subscriptions, one-shot payments and webhook handling.
- **Notifications_Service**: The reactive service consuming events to send emails (Resend) and push notifications (Expo Push).
- **Analytics_Service**: The reactive service ingesting events into Tinybird / ClickHouse for time-series analytics.
- **AI_Coach_Service**: The service providing LLM-based coaching features (Vercel AI SDK + Mistral).
- **Mobile_App**: The Expo SDK 58 / React Native 0.88 client application.
- **Web_App**: The Next.js 16 member-facing web client.
- **Studio_Admin_App**: The Next.js 16 web client for studio administrators and coaches.
- **Event_Bus**: The combination of Cloudflare Queues (real-time side-effects, retry + DLQ) and Upstash QStash (scheduled jobs, cron).
- **Mutation_Queue**: The persistent FIFO queue (MMKV) on the Mobile_App buffering write operations while offline.
- **Rate_Limiter**: The sliding-window rate limiter backed by Upstash Redis applied by the API_Gateway.
- **RLS_Policies**: PostgreSQL Row Level Security policies enforcing tenant isolation on Neon.
- **Audit_Log**: The append-only `audit_log` table storing actor-action-target records.
- **QR_Checkin_Token**: A short-lived (120 seconds) JWT RS256 generated by the Mobile_App and verified by the Reservations_Service for physical access.
- **Studio**: A tenant (boutique studio, gym chain, independent coach) with its own members, classes and branding.
- **Consents**: A versioned JSON record (`marketing`, `analytics`, `thirdParty`, `version`, `updatedAt`) stored per user.
- **Idempotency_Key**: A client-generated UUID v4 sent in the `Idempotency-Key` HTTP header to guarantee at-most-once server-side application of a mutation.

## Requirements

### Requirement 1: Member Registration and Login

**User Story:** As a new member, I want to create an account with my email, an OAuth provider or Apple Sign-In, so that I can access my studio's services.

#### Acceptance Criteria

1. WHEN a user submits a registration form with email, password, display name, studio slug and a consent record, THE Auth_Service SHALL create a new user bound to the resolved studio, hash the password with bcrypt at cost greater than or equal to 12, and return an access token and a refresh token.
2. IF the submitted password appears in the Have-I-Been-Pwned breached-password database, THEN THE Auth_Service SHALL reject the registration with HTTP 422 and a `password_breached` error code.
3. WHEN an iOS user initiates registration or login, THE Mobile_App SHALL offer Apple Sign-In as an available authentication method.
4. WHEN a user presents an Apple or Google ID token, THE Auth_Service SHALL validate the token's signature against the provider's JWKS as part of processing the request, and SHALL only create or link the local user account and issue tokens when validation succeeds.
5. WHEN a user submits valid email and password credentials, THE Auth_Service SHALL return an access token valid for 15 minutes and a refresh token valid for 30 days.
6. IF more than 5 failed login attempts are observed for the same (IP, email) pair within a 15-minute sliding window, THEN THE Auth_Service SHALL reject further login attempts with HTTP 429 and a `Retry-After` header until the window expires.
7. WHERE the device supports biometric authentication, THE Mobile_App SHALL allow the user to unlock a stored refresh token using Face ID, Touch ID or Android biometrics before calling the refresh endpoint.

### Requirement 2: Session Management

**User Story:** As a platform operator, I want access tokens and refresh tokens managed with strict lifetimes and rotation, so that compromised tokens have a bounded impact.

#### Acceptance Criteria

1. THE Auth_Service SHALL sign access tokens using RS256 with an expiration 15 minutes after issuance.
2. WHEN a refresh token is exchanged for a new access token, THE Auth_Service SHALL rotate the refresh token, issuing a new one and invalidating the previous one.
3. THE Auth_Service SHALL store refresh tokens as httpOnly, Secure, SameSite=Lax cookies on web clients.
4. IF a refresh token is presented after its 30-day expiration, THEN THE Auth_Service SHALL reject the request with HTTP 401, force re-authentication, append a `token.expired.presented` record to the Audit_Log, and count the attempt against the `(IP, user)` sliding-window rate limit.
5. WHEN an access token expires during an authenticated session, THE API_Gateway SHALL respond with HTTP 401 and the header `WWW-Authenticate: Bearer error="token_expired"`.

### Requirement 3: Member Profile Management

**User Story:** As a member, I want to view and update my profile information and consents, so that my personal data stays accurate and aligned with my preferences.

#### Acceptance Criteria

1. WHEN an authenticated member requests their profile, THE Members_Service SHALL return the member's record including `id`, `studioId`, `email`, `displayName`, `avatarUrl`, `role` and current `consents`.
2. WHEN a member submits a profile patch, THE Members_Service SHALL validate the payload against the Zod schema and persist only the fields allowed by the patch whitelist.
3. WHEN a member updates their consents, THE Members_Service SHALL replace the `consents` JSON value with a new record containing the updated flags, the current CGU version identifier and `updatedAt = now()`.
4. THE Members_Service SHALL reject display names whose trimmed length is zero or strictly greater than 80 characters with HTTP 422.
5. WHERE the requesting user has role `admin` or `coach` within a studio, THE Members_Service SHALL return a paginated list of member profiles belonging to that same studio when a list request is made.

### Requirement 4: RGPD Data Export

**User Story:** As a member, I want to export all personal data the platform holds about me, so that I can exercise my right to portability.

#### Acceptance Criteria

1. WHEN an authenticated member requests a data export, THE Members_Service SHALL enqueue an asynchronous export job and return an export job identifier with HTTP 202.
2. WHEN an export job completes, THE Members_Service SHALL produce a ZIP archive containing all personal data in JSON and CSV form, upload it to Cloudflare R2, and send the member an email (via Resend) containing a signed download link that expires 72 hours after issuance.
3. THE Members_Service SHALL complete the export and deliver the email within 48 hours of the request.
4. THE export archive SHALL contain at minimum the member's profile, consents history, reservations, workout sessions, check-in records and billing invoices owned by the member.

### Requirement 5: RGPD Account Deletion

**User Story:** As a member, I want to permanently delete my account and all associated personal data, so that I can exercise my right to erasure.

#### Acceptance Criteria

1. WHEN an authenticated member requests account deletion, THE Auth_Service SHALL mark the user as soft-deleted by setting `deleted_at = now()` and publish an `auth.user.deleted` event on the Event_Bus.
2. WHEN the `auth.user.deleted` event is consumed, THE Athlya_Platform SHALL cascade-delete reservations, workout sessions and push tokens owned by the user, and purge avatar binaries from Cloudflare R2.
3. WHEN 30 days have elapsed since a user's `deleted_at` timestamp, THE Athlya_Platform SHALL anonymize every row of the Audit_Log referencing that user by invoking the PostgreSQL `SECURITY DEFINER` function `anonymize_user_audit(user_id uuid)` exclusively; this function SHALL set `actor_id = NULL` and remove personally identifying fields from the `metadata` JSON, and SHALL be the ONLY execution path that mutates the Audit_Log. No direct `UPDATE` or `DELETE` statement (outside this function) SHALL ever succeed against the Audit_Log, regardless of the requester's role.
4. WHEN 30 days have elapsed since a user's `deleted_at` timestamp, THE Athlya_Platform SHALL guarantee that no row in `users`, `reservations`, `workout_sessions` or any table joined to that user by foreign key remains retrievable.
5. THE Athlya_Platform SHALL host member personal data exclusively in European Union regions (Neon Frankfurt, Cloudflare EU PoPs, Upstash EU, Resend EU).

### Requirement 6: Class Planning (Studio Admin)

**User Story:** As a studio administrator, I want to create and edit classes in the weekly schedule, so that members can see and book them.

#### Acceptance Criteria

1. WHEN an authenticated user with role `admin` submits a new class with `title`, `startsAt`, `durationMin`, `capacity` and optionally `coachId`, THE Content_Service SHALL persist the class bound to the admin's studio with `version = 0`.
2. THE Content_Service SHALL reject class creation when `capacity` is not in the inclusive range [1, 500] with HTTP 422.
3. THE Content_Service SHALL reject class creation when `durationMin` is not in the inclusive range [5, 480] with HTTP 422.
4. IF the submitted `startsAt` is earlier than the server's current time, THEN THE Content_Service SHALL reject the creation request with HTTP 422.
5. WHEN a non-admin user attempts to update an existing class, THE Content_Service SHALL reject the request with HTTP 403 without performing version validation.
6. WHEN an authenticated admin updates an existing class, THE Content_Service SHALL require the client to submit the current `version` and SHALL reject the update with HTTP 409 when the submitted version does not match the persisted version.
7. WHEN a class update succeeds, THE Content_Service SHALL increment the class's `version` by 1.

### Requirement 7: Class Browsing

**User Story:** As a member, I want to browse upcoming classes for my studio, so that I can decide which ones to book.

#### Acceptance Criteria

1. WHEN an authenticated member requests the class list for a date range, THE Reservations_Service SHALL return all non-deleted classes of the member's studio whose `startsAt` falls within the requested range, ordered by `startsAt` ascending.
2. THE Reservations_Service SHALL include for each class the current `remaining` seat count read from the Redis counter.
3. IF the requested date range exceeds 90 days, THEN THE Reservations_Service SHALL reject the request with HTTP 422 and a `range_too_large` error code.

### Requirement 8: Class Reservation Without Double-Booking

**User Story:** As a member, I want to reserve a class in a single tap, so that I can secure a seat quickly even when many members book simultaneously.

#### Acceptance Criteria

1. WHEN an authenticated member submits a booking request for a class with available capacity, THE Reservations_Service SHALL create a reservation with `status = 'confirmed'` and publish a `reservation.created` event.
2. WHEN an authenticated member submits a booking request for a class whose confirmed reservations have reached its `capacity`, THE Reservations_Service SHALL create a reservation with `status = 'waitlist'` and publish a `reservation.waitlisted` event, returning the member's position in the waitlist.
3. THE Reservations_Service SHALL maintain the invariant that for every class `c`, the count of reservations with `status = 'confirmed'` for `c` is less than or equal to `c.capacity` at every instant observable externally.
4. WHEN the same `(user_id, class_id)` pair is submitted more than once, THE Reservations_Service SHALL create at most one reservation row enforced by the SQL unique constraint.
5. WHEN a booking request carries an `Idempotency-Key` header that matches a previously processed request from the same user, THE Reservations_Service SHALL return the previously produced result without creating a new reservation.
6. IF the target class has `startsAt` earlier than or equal to the server's current time, THEN THE Reservations_Service SHALL reject the booking with HTTP 422 and a `class_in_past` error code.

### Requirement 9: Reservation Cancellation and Waitlist Promotion

**User Story:** As a member, I want to cancel a reservation up to 2 hours before the class starts, so that my seat can be freed for the next person on the waitlist.

#### Acceptance Criteria

1. WHEN an authenticated member cancels a reservation they own whose class `startsAt` is at least 2 hours after `now()`, THE Reservations_Service SHALL set the reservation's `status` to `'cancelled'` and `cancelled_at` to `now()`.
2. IF a cancellation is requested less than 2 hours before the class `startsAt`, THEN THE Reservations_Service SHALL reject the request with HTTP 422 and a `cancellation_window_closed` error code.
3. WHEN a confirmed reservation is successfully cancelled (all validation checks passed) and at least one reservation with `status = 'waitlist'` exists for the same class, THE Reservations_Service SHALL promote the oldest waitlisted reservation (FIFO by `created_at`) to `status = 'confirmed'` within the same database transaction and publish a `reservation.promoted` event.
4. WHEN a confirmed reservation is cancelled and no waitlisted reservation exists for the same class, THE Reservations_Service SHALL increment the Redis `class:{id}:remaining` counter by 1.
5. THE Reservations_Service SHALL emit exactly one `reservation.cancelled` event per successful cancellation.

### Requirement 10: Reservation State Transitions

**User Story:** As a platform operator, I want reservation states to follow a strict state machine, so that historical data remains consistent and auditable.

#### Acceptance Criteria

1. THE Reservations_Service SHALL allow transitions only along the paths `confirmed → cancelled`, `confirmed → no_show`, `waitlist → confirmed` and `waitlist → cancelled`.
2. WHERE the requested transition is from a status to the same status (for example `confirmed → confirmed`), THE Reservations_Service SHALL treat the request as a no-op and return HTTP 200 without modifying the reservation.
3. IF any other transition is requested, THEN THE Reservations_Service SHALL reject the request with HTTP 422 and an `invalid_transition` error code.
4. THE Reservations_Service SHALL never transition a reservation from `cancelled` back to `confirmed`.
5. THE Reservations_Service SHALL allow a member to cancel their own reservation when its status is `confirmed` or `waitlist`.

### Requirement 11: QR Check-in Token Generation and Verification

**User Story:** As a member, I want to enter the gym by showing a QR code on my phone, so that I do not need a physical card or a screenshot.

#### Acceptance Criteria

1. WHEN the Mobile_App displays the check-in screen for a signed-in member, THE Mobile_App SHALL generate a QR_Checkin_Token as a JWT RS256 whose payload contains `sub = userId`, `studio = studioId`, `kind = 'checkin'`, `iat = now()`, `exp = now() + 120` seconds, and a fresh `jti` UUID v4.
2. WHEN a QR_Checkin_Token is presented to the check-in endpoint, THE Reservations_Service SHALL verify the RS256 signature, `kind === 'checkin'`, `studio === expectedStudioId`, and `iat ≤ now() ≤ exp` before any database read.
3. IF the submitted QR_Checkin_Token fails any signature, payload or time-window verification, THEN THE Reservations_Service SHALL reject the check-in with HTTP 401 and a `invalid_token` error code.
4. WHEN a QR_Checkin_Token is successfully consumed, THE Reservations_Service SHALL store the token's `jti` in a Redis set with TTL 120 seconds.
5. IF a QR_Checkin_Token's `jti` already exists in the replay-prevention Redis set within its validity window, THEN THE Reservations_Service SHALL reject the check-in with HTTP 401 and a `replay` error code.
6. WHEN a check-in succeeds, THE Reservations_Service SHALL locate the member's confirmed reservation whose class `startsAt` falls within `[now() - 30 min, now() + 30 min]` and SHALL set `checked_in_at = now()` on that reservation.

### Requirement 12: Workout Session Logging

**User Story:** As a member, I want to log my workout sessions with exercises, sets, reps and weights, so that I can track my progression over time.

#### Acceptance Criteria

1. WHEN an authenticated member submits a workout session, THE Members_Service SHALL persist the session with `user_id`, `started_at`, `duration_min`, `exercises`, optional `notes` and `studio_id` when applicable.
2. THE Members_Service SHALL reject workout sessions containing more than 50 exercises with HTTP 422.
3. THE Members_Service SHALL reject any exercise containing more than 30 sets with HTTP 422.
4. WHEN an authenticated member requests their workout session history for a time window, THE Members_Service SHALL return sessions ordered by `started_at` descending.

### Requirement 13: Multi-tenant Isolation Via RLS

**User Story:** As a studio administrator, I want strong guarantees that members from other studios cannot read or modify my studio's data, so that I can trust the platform with sensitive member information.

#### Acceptance Criteria

1. WHEN the API_Gateway opens a database transaction on behalf of an authenticated user, THE API_Gateway SHALL set the PostgreSQL session variables `app.user_id`, `app.studio_id` and `app.role` from the verified JWT claims using `SET LOCAL`.
2. THE RLS_Policies SHALL restrict `SELECT` on `users` to the requesting user's own row unless the requester's role is `admin` or `coach` and the target row's `studio_id` matches the requester's `studio_id`.
3. THE RLS_Policies SHALL restrict `SELECT` on `reservations` to rows whose `user_id` equals `current_setting('app.user_id')`.
4. THE RLS_Policies SHALL restrict `SELECT` on `audit_log` to requesters whose role is `admin`.
5. IF an authenticated request attempts to read, modify or delete a row belonging to a different studio, THEN THE Athlya_Platform SHALL return HTTP 404 (not 403) so that resource existence is not disclosed, regardless of the user's role or permissions within their own studio.
6. THE RLS_Policies SHALL be enabled on every table containing tenant data in every environment including production.

### Requirement 14: API Gateway Request Pipeline

**User Story:** As a security engineer, I want every request to pass through a consistent pipeline of authentication, rate limiting, validation and tracing, so that defense-in-depth is enforced uniformly.

#### Acceptance Criteria

1. WHEN a request arrives at the API_Gateway, THE API_Gateway SHALL verify the JWT RS256 signature against the current JWKS before invoking any domain service.
2. THE API_Gateway SHALL validate every request body, query and path parameter against the relevant Zod schema exported from `packages/shared`.
3. IF the Rate_Limiter observes more than 100 requests per second for a given client IP, THEN THE API_Gateway SHALL respond with HTTP 429 and a `Retry-After` header computed from the sliding window.
4. IF the Rate_Limiter observes more than 500 requests per second for a given authenticated user, THEN THE API_Gateway SHALL respond with HTTP 429 and a `Retry-After` header computed from the sliding window.
5. THE API_Gateway SHALL propagate the W3C `traceparent` header through every downstream call and emit OpenTelemetry spans to the configured OTLP/HTTP endpoint (default target: Axiom; Baselime is deprecated and removed from supported targets as of May 2026).
6. THE API_Gateway SHALL serialize every error response as `application/problem+json` following RFC 7807 with `type`, `title`, `status` and `traceId` fields.

### Requirement 15: Sliding-Window Rate Limiting

**User Story:** As a platform operator, I want the rate limiter to enforce exact sliding-window quotas, so that abusive clients cannot exceed configured limits.

#### Acceptance Criteria

1. THE Rate_Limiter SHALL return `Allow` for a given `(key, limit, windowSec)` if and only if the number of requests recorded for `key` in the interval `(now - windowSec, now]` is less than or equal to `limit`.
2. WHEN the Rate_Limiter returns `Deny`, THE Rate_Limiter SHALL include a `retryAfterSec` value computed from the timestamp of the oldest request in the window.
3. THE Rate_Limiter SHALL implement the sliding window using a Redis sorted set pipeline (`ZREMRANGEBYSCORE` + `ZADD` + `ZCARD` + `EXPIRE`) executed in a single round-trip.

### Requirement 16: Event Bus Delivery and Transactional Outbox

**User Story:** As a platform operator, I want events to be delivered reliably even when the event bus is temporarily unavailable, so that side-effects like notifications are not lost.

#### Acceptance Criteria

1. WHEN a domain service commits a state change, THE domain service SHALL publish the corresponding event on the Event_Bus.
2. IF publication on Cloudflare Queues fails after the configured retry budget, THEN THE domain service SHALL insert the event into a PostgreSQL `outbox` table within the same transaction as the primary state change, regardless of whether the final retry attempt eventually succeeded after the budget was exhausted.
3. IF the `outbox` insertion fails, THEN THE domain service SHALL roll back the entire transaction including the primary state change.
4. THE Athlya_Platform SHALL run a background worker that drains the `outbox` table to the Event_Bus at least every 30 seconds and removes rows that are successfully republished.
5. WHEN an Event_Bus consumer fails to process an event 5 consecutive times, THE Event_Bus SHALL route the event to a dead-letter queue.

### Requirement 17: Notifications Delivery with Consent Enforcement

**User Story:** As a member, I want notifications to respect my consent preferences, so that I only receive communications I have agreed to.

#### Acceptance Criteria

1. WHEN the Notifications_Service consumes an event requiring a member-facing message, THE Notifications_Service SHALL read the recipient's current `consents` and SHALL send the message only if the relevant consent flag is true.
2. THE Notifications_Service SHALL always send transactional messages related to reservation confirmation, cancellation, check-in and billing regardless of the `marketing` consent flag.
3. WHEN a `reservation.created` event is consumed, THE Notifications_Service SHALL schedule a `reservation.reminder` job in Upstash QStash to fire exactly 1 hour before the class `startsAt`.
4. WHEN the Notifications_Service processes an event, THE Notifications_Service SHALL deduplicate against the `event.id` stored in Redis with TTL 24 hours so that retried events do not produce duplicate notifications.

### Requirement 18: Payments and Subscriptions

**User Story:** As a member, I want to pay for a monthly subscription through Stripe, so that I can access my studio's services.

#### Acceptance Criteria

1. WHEN an authenticated member initiates a subscription checkout, THE Billing_Service SHALL create a Stripe Checkout session scoped to the member's studio Stripe account and return its URL.
2. WHEN Stripe delivers a `checkout.session.completed` webhook, THE Billing_Service SHALL verify the webhook signature before processing the payload.
3. IF a Stripe webhook signature verification fails, THEN THE Billing_Service SHALL reject the request with HTTP 400 and atomically append an entry to the Audit_Log; both actions SHALL succeed together or the whole operation SHALL fail.
4. WHEN Stripe delivers a `customer.subscription.created` event, THE Billing_Service SHALL persist the subscription and publish a `billing.subscription.started` event.
5. WHEN Stripe delivers a `invoice.payment_failed` event, THE Billing_Service SHALL publish a `billing.subscription.failed` event consumed by the Notifications_Service.

### Requirement 19: Offline-capable Mobile Writes

**User Story:** As a member, I want to continue using the app without a network, so that transient connectivity loss does not break my workflow.

#### Acceptance Criteria

1. WHILE the Mobile_App detects no internet connectivity, THE Mobile_App SHALL enqueue mutation intents (for example `logSession`, `bookClass`, `cancelReservation`) in the Mutation_Queue persisted in MMKV with a unique `Idempotency_Key`.
2. THE Mobile_App SHALL remain operational in read mode for at least 72 hours using only data cached in MMKV.
3. WHEN the Mobile_App detects that internet connectivity has been restored, THE Mobile_App SHALL drain the Mutation_Queue in FIFO order.
4. WHILE draining, THE Mobile_App SHALL send each enqueued mutation with its `Idempotency-Key` header and SHALL remove the entry from the queue when the server returns a 2xx status code or HTTP 409.
5. IF the server returns an HTTP 4xx status other than 409 for a mutation that was successfully transmitted, THEN THE Mobile_App SHALL move the mutation to a local dead-letter queue and remove it from the active queue.
6. IF the request fails before the server receives the mutation (network error, DNS failure, TLS error), THEN THE Mobile_App SHALL retry with exponential backoff up to 5 attempts with jitter, keeping the mutation in the queue if all attempts fail.
7. IF the server returns an HTTP 5xx status, THEN THE Mobile_App SHALL retry with exponential backoff up to 5 attempts with jitter, keeping the mutation in the queue if all attempts fail.

### Requirement 20: Idempotent Mutations

**User Story:** As a client developer, I want mutations to be idempotent when retried with the same key, so that retries never create duplicates.

#### Acceptance Criteria

1. WHEN a mutation request carries an `Idempotency-Key` header matching a request the server has already applied successfully, THE API_Gateway SHALL return the previously stored response without re-executing the mutation, even when the original client never received the original response.
2. THE API_Gateway SHALL persist idempotency key bindings for at least 24 hours.
3. THE Mobile_App SHALL generate an `Idempotency-Key` as a fresh UUID v4 for every mutation enqueued in the Mutation_Queue.

### Requirement 21: Configuration Serialization Round-Trip

**User Story:** As a platform engineer, I want domain objects and their serialized forms to round-trip losslessly, so that clients and servers can exchange data without information loss.

#### Acceptance Criteria

1. THE Athlya_Platform SHALL provide a JSON serializer for every domain model exposed by the public API (Studio, User, Class, Reservation, WorkoutSession, AuditLog).
2. THE Athlya_Platform SHALL provide a JSON deserializer (Zod parser) for every domain model exposed by the public API.
3. FOR ALL valid domain objects, deserializing the output of the serializer SHALL produce an object structurally equivalent to the original (round-trip property).
4. THE Athlya_Platform SHALL validate that every API response conforms to the output Zod schema of the endpoint before serialization.

### Requirement 22: Audit Logging

**User Story:** As a studio administrator, I want an immutable record of security-relevant actions, so that I can investigate incidents.

#### Acceptance Criteria

1. WHEN any of the following actions occurs — user registration, user deletion, reservation cancellation by admin, RLS violation attempt, Stripe webhook signature failure — THE Athlya_Platform SHALL append a row to the Audit_Log containing `actor_id`, `action`, `target_type`, `target_id`, `metadata` and `created_at`.
2. THE RLS_Policies SHALL deny `UPDATE` and `DELETE` on the Audit_Log for every role, including `admin`, the application's `athlya_app` role, and the cron worker's `athlya_cron` role. The Audit_Log SHALL be completely immutable and append-only from every direct SQL path.
3. WHERE an RGPD anonymization is required by Requirement 5.3, THE Athlya_Platform SHALL mutate the Audit_Log exclusively through the `SECURITY DEFINER` function `anonymize_user_audit(user_id uuid)`, owned by a dedicated `athlya_owner` role, with `EXECUTE` privilege granted only to `athlya_cron`; no other mutation path SHALL be authorized.
4. THE Audit_Log SHALL be readable only by users whose role is `admin` and scoped to their own studio.

### Requirement 23: Reservation API Performance

**User Story:** As a member, I want the reservation flow to feel instantaneous, so that my booking succeeds even when the studio opens a popular class.

#### Acceptance Criteria

1. WHEN the Reservations_Service processes a `POST /v1/reservations` request under nominal load, THE Reservations_Service SHALL return a response with p50 latency less than 100 milliseconds measured over a 5-minute rolling window.
2. WHEN the Reservations_Service processes a `POST /v1/reservations` request under nominal load, THE Reservations_Service SHALL return a response with p99 latency less than 500 milliseconds measured over a 5-minute rolling window.
3. THE API_Gateway SHALL exhibit a Cloudflare Worker cold start of less than 50 milliseconds at the 95th percentile.

### Requirement 24: Availability

**User Story:** As a studio operator, I want the platform to be highly available, so that my business is not disrupted by infrastructure incidents.

#### Acceptance Criteria

1. THE Athlya_Platform SHALL achieve a monthly availability of at least 99.9% measured against the reservation endpoints.
2. WHEN a downstream service exceeds 5 consecutive failures within 30 seconds, THE API_Gateway SHALL open a circuit breaker for that service and respond with HTTP 503 and `Retry-After: 2` for 60 seconds before entering half-open state.

### Requirement 25: Transport Security and Security Headers

**User Story:** As a security engineer, I want strong transport and browser security controls applied to every response, so that common web attacks are mitigated by default.

#### Acceptance Criteria

1. THE API_Gateway SHALL accept only TLS 1.3 connections.
2. THE API_Gateway SHALL include the header `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` on every response.
3. THE Web_App SHALL serve every HTML response with a strict Content-Security-Policy using per-request nonces for inline scripts.
4. THE Web_App SHALL serve every response with `X-Frame-Options: DENY` and `Referrer-Policy: strict-origin`.
5. WHEN a JWT signing key has been in service for 90 days, THE Auth_Service SHALL rotate the signing key and publish the new public key at `/.well-known/jwks.json` while keeping the previous key valid for a grace period.

### Requirement 26: Bot and Abuse Protection

**User Story:** As a platform operator, I want automated bot traffic on authentication surfaces to be filtered, so that credential stuffing and spam registrations are mitigated.

#### Acceptance Criteria

1. WHEN a registration form is submitted, THE Web_App SHALL require a valid Cloudflare Turnstile token and THE API_Gateway SHALL verify this token before forwarding the request to the Auth_Service.
2. WHEN a login form is submitted from the Web_App, THE Web_App SHALL include a valid Cloudflare Turnstile token and THE API_Gateway SHALL verify this token before forwarding the request to the Auth_Service.
3. IF a Turnstile verification fails, THEN THE API_Gateway SHALL reject the request with HTTP 403, a `bot_challenge_failed` error code, and SHALL NOT forward the request to the Auth_Service.

### Requirement 27: Web Accessibility

**User Story:** As a member with disabilities, I want the web application to be fully accessible, so that I can use the platform with assistive technologies.

#### Acceptance Criteria

1. THE Web_App SHALL conform to WCAG 2.2 Level AA success criteria as evaluated by automated checks (axe-core) in CI.
2. THE Web_App SHALL pass Lighthouse Accessibility score greater than or equal to 95 on every MVP-critical page.
3. THE Mobile_App SHALL expose accessible labels, roles and hints for every interactive component so that VoiceOver and TalkBack can operate the app.

### Requirement 28: Internationalization

**User Story:** As a user, I want to use the platform in my preferred language, so that I understand every interface element.

#### Acceptance Criteria

1. THE Athlya_Platform SHALL support French and English user interfaces for every user-facing string at v1.
2. WHEN a client sends an `Accept-Language` header, THE API_Gateway SHALL select the matching locale from the supported set and include the selected locale in error response `detail` fields.
3. THE Athlya_Platform SHALL source all user-facing strings from locale files in `packages/shared/i18n` with no hard-coded strings in UI components.

### Requirement 29: OWASP Top 10 Coverage

**User Story:** As a security engineer, I want automated checks for the OWASP Top 10 risks, so that regressions are caught before production.

#### Acceptance Criteria

1. THE Athlya_Platform SHALL run an OWASP ZAP baseline scan on every pull request and SHALL block merge to `main` when any high-severity finding is reported.
2. THE Athlya_Platform SHALL run a daily dependency scan (Socket.dev or Snyk) against the lockfile and SHALL fail the nightly build when a critical vulnerability is reported.
3. THE Athlya_Platform SHALL run pgTAP tests for RLS policies on every pull request touching SQL migrations.

### Requirement 30: Observability

**User Story:** As an on-call engineer, I want distributed traces, structured logs and error reports for every request, so that I can diagnose production incidents quickly.

#### Acceptance Criteria

1. THE API_Gateway SHALL emit an OpenTelemetry span for every incoming request with the attributes `http.method`, `http.route`, `http.status_code`, `studio.id` (when known) and `user.id` (when known).
2. THE API_Gateway SHALL forward every emitted span to the configured OTLP/HTTP endpoint (default target: Axiom). The target SHALL be configurable via `OTEL_EXPORTER_OTLP_ENDPOINT` without code change.
3. WHEN an unhandled exception occurs in a Worker, THE API_Gateway SHALL attempt to capture it in Sentry with the `traceId` as a tag, and SHALL continue processing the response even if the Sentry capture call fails.
4. THE Athlya_Platform SHALL log every request in structured JSON containing at minimum `timestamp`, `traceId`, `method`, `path`, `status` and `durationMs`.
